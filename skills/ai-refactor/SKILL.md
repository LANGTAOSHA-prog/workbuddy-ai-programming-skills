# ai-refactor — 智能重构助手

在动笔改代码之前,先定位「该改哪」,再给出「怎么改」,最后给可落地的补丁或分步计划。
不做无根据的大改,遵循「小步、可测试、行为不变」的重构纪律。

## 何时使用

- 用户主动要求重构、拆分、精简某段代码
- 代码过长、嵌套深、参数多、重复逻辑多
- 准备加功能前,想先理清楚结构
- Code review 中识别出 code smell,需要给出具体改法

## 工作流程

### 1. 定位味道(可选但推荐)

先用随附脚本对目标文件/目录做静态扫描,拿到客观指标,再据此给建议:

```bash
python3 scripts/analyze_smells.py PATH [PATH ...] \
  --max-lines 60 --max-params 4 --max-depth 4 [--json]
```

脚本会报告:

- **函数过长**(行数 > 阈值)
- **参数过多**(> 阈值,通常意味着可聚合为对象/配置)
- **嵌套过深**(if/for/while 层层包裹,应早返回或提取)
- **圈复杂度偏高**(决策点过多,应拆分)

Python 用 `ast` 精确解析,JS/TS 用轻量正则扫描(足够定位明显味道)。
可用 `--json` 输出结构化结果喂给后续生成。

### 2. 给出重构方案(不要直接动手改用户文件)

按优先级输出:

1. **目标与风险**:重构后行为不变的契约是什么?哪些测试/调用方会受影响?
2. **具体手法**:明确指出用哪类重构(提取函数 / 提取变量 / 早返回 / 引入参数对象 /
   策略模式 / 用管道替代循环 / 卫语句替代嵌套 if)。
3. **前后对照**:贴出关键片段的 before / after,改动最小化。
4. **落地步骤**:分小步,每步可独立验证(编译/测试通过)。

### 3. 产出补丁(用户确认后)

- 如需直接改文件,先用 Edit 工具做小范围、可回滚的修改。
- 复杂重构分批提交,每批单独可测。
- 改完建议跑测试/类型检查确认行为不变。

## 常见重构映射(来自脚本指标)

| 指标 | 典型手法 |
|------|----------|
| 函数过长 | 提取子函数、按职责拆分 |
| 参数过多 | 引入参数对象 / 配置结构体 |
| 嵌套过深 | 卫语句(早返回)、提取函数、表驱动 |
| 圈复杂度高 | 拆分条件、策略/多态、抽取纯函数 |
| 重复代码 | 提取公共函数 / 模板方法 |

## 反模式

- 没看代码就大谈「应该微服务化」「全部重寫」之类的空话
- 一次改一大片且无法回滚
- 改变外部行为却没提醒调用方
- 忽略现有测试,重构后不验证
- 把脚本扫不到的上下文(框架约定、性能敏感路径)当成普通 smell 一刀切
